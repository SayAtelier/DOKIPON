GemArc Commerce — 消费者端 HTML 原型

本套原型是 DOKIPON 仓库中真正在跑的产品线（电商交易系统）的静态等价物： 三端（App / Web / LINE MINI App）共用同一套 Flutter 组件与状态控制器。 页面上的每一个字段、每一句文案、每一条状态分支，都取自源码， 而不是设计师的想象 —— 数据为演示值，交互规则为真实规则。

真实实现现状 / What the code actually does

原型照客户端期望渲染。这一节记录真实代码与该期望的差距。 最初的版本列出 6 类接线缺口；它们现在都已闭合，下面是闭合方式与证据。

① 12 条路径由一个进程提供 —— commerce-edge

已闭合。 新增 services/crates/commerce-edge：把 9 个 commerce 服务挂进 同一个 axum Router，按路径前缀 dispatch （route_for()），价格权威走进程内而不会回调自己。 未匹配的路径由 edge 兜底 404，而不是落到最后一个服务。

commerce-bff 不再是「只有 4 条路由且 2 个是桩」的状态： /v1/sessions/guest 与 POST /v1/checkouts 由真实实现（LIFF id_token 校验 + nonce 防重放、订单状态机 + 幂等记录）承担。 客户端仍然只需要一个 baseUri。

② snake_case ↔ camelCase 漂移 —— 已由服务端对齐

已闭合（服务端侧）。 契约 contracts/openapi.yaml 是 camelCase，服务端过去发的是 snake_case，Dart 客户端只读 camelCase —— 字段会静默变空（产品没标题、 订单显示 ¥0、游客会话 id 为空）。 现在各服务按契约逐字段对齐：
字段现在后果
productIdcamelCase正常
stockPolicycamelCase库存 Saga 判断正确
channelEligibilitycamelCase渠道政策排除生效
titleI18ncamelCase标题不再为空
sessionIdcamelCase游客会话 id 不再为空
lines[].unitAmount / total.amountMinorcamelCase订单不再显示 ¥0
客户端仍保留双读兜底（camel 优先、snake 兜底）。这不是 workaround， 而是让客户端同时兼容对齐前后的服务端。

③ 分类过滤 —— 契约里的 categoryId 现在真的接上了

已闭合。 GET /v1/products 一直声明了 categoryId， 服务端也一直按 category_id 过滤，但客户端从没有这个概念 —— 分类条上的按钮是 onTap: () {}，点不动。 现在：CatalogController.selectCategory() 换分类是替换列表 而不是追加，过滤器随 cursor 一起走，上一个分类还在飞的请求会被丢弃 （query id 守卫），不会覆盖用户已经选中的分类。 demo 目录也覆盖了导航条提供的全部分类 —— 一个大半入口通向空货架的 demo 会让能用的过滤器看起来像坏的。

仍然存在的限制（如实记录）

  • inventory 没有列表路由。 inventory 服务只有三条预留写路由，没有读路由，因此 GET /v1/inventory 是 404， GET /admin/v1/inventory 也会回 admin.upstream_error。契约里标着 x-implemented: false 与 x-blocked-by: inventory-service-has-no-list-route。
  • 状态在内存里。 购物车、订单、库存都是进程内状态，Vercel 可能同时跑多个函数实例， 跨实例的购物车会「凭空清空」。目录、内容文档与运营后台是静态或幂等读，不受影响。 要变成生产部署，需要把可变存储搬进共享数据库 —— 改的是 store，不是 edge。
  • 运营后台的字段名仍是游戏域词汇。 界面已电商化，后端返回的 playerId / vipLevel / guild / mall 没改 —— 逐屏对照表见运营后台索引页。

怎么用 / How to use

  • 直接双击 index.html 打开，无需构建、无需起服务、无网络请求。
  • 每屏右侧的说明面板标注了它对应的 API、源码位置与可复现的操作。
  • 数据全部内置在 assets/storefront.js，时间戳相对打开时刻生成。
  • 另一套（游戏线遗留的）运营后台原型在 ../admin-console/。
