GemArc Commerce — 消费者端 HTML 原型

本套原型是 DOKIPON 仓库中真正在跑的产品线（电商交易系统）的静态等价物： 三端（App / Web / LINE MINI App）共用同一套 Flutter 组件与状态控制器。 页面上的每一个字段、每一句文案、每一条状态分支，都取自源码， 而不是设计师的想象 —— 数据为演示值，交互规则为真实规则。

依据：packages/design_system 依据：packages/domain_models 依据：packages/storefront_state 依据：packages/api_client 依据：contracts/openapi.yaml 依据：services/crates/commerce-*

各画面右側の説明パネルは日本語で記載しています（電商線の設計書 docs/ecommerce/ と同じ言語）。

真实实现现状 / What the code actually does

原型照客户端期望渲染。但把 openapi 契约、服务端实现和 Dart 客户端三方对齐后， 电商线上仍有 6 类接线缺口（另有 1 处低影响项）。这部分不是原型能补的，需要真实改动，所以在此如实列出。

① 12 条契约路径分别落在 5 个独立进程里，没有网关

路径实现位置行号

BFF 不代理另外四个服务，而且它自己的两个端点是桩。 commerce-bff/src/main.rs 的 router 只有 4 条路由，且全文件没有 HTTP 客户端； submit_checkout 只校验 session 与 Idempotency-Key 就返回 202 空体（main.rs:215-219）， guest_session 本地造一个 id（main.rs:167-179）。 而 Dart 客户端只有一个 baseUri（commerce_api_client.dart:12/35）。 仓库里也没有电商线的网关/ingress 清单（docker/compose 里是游戏侧 5 域）。 → 结论：12 条路径全部有实现，但没有任何一个进程能同时提供它们； 客户端若指向 BFF，拿到的是 checkout 的空 202 与本地造的游客会话， 而 /v1/sessions/line 只在 identity 里 —— 从 BFF 出发根本换不到 LINE 会话，LINE 登录链路当前不可达。
两条路径有两套实现，谁生效取决于 baseUri 指向谁。 /v1/sessions/guest 与 POST /v1/checkouts 在 BFF 与 identity / order 里各有一份：BFF 版是边缘桩，identity/order 版才有真实语义 （LIFF id_token 校验 + nonce 防重放、订单状态机 + 幂等记录）。 这是接线时最容易踩的一处：同一路径，不同行为。

已正确处理、不必改的部分： next_cursor、cart_id、unit_amount_snapshot、 expires_at_ms 在 Dart 侧都写了双读兜底（snake 优先，camel 兜底）； checkout 快照与订单外层字段由 json! 直接拼装，本就是 camelCase。

③ 设计书要求、代码尚未覆盖的语义

  • 渠道过滤是服务端职责：catalog.list_products 按 channel 过滤，客户端只负责带对 x-channel 头。
  • 价格以服务端为准：commerce-core::Money 是整数最小单位 + ISO-4217，客户端的小计只用于显示。
  • 幂等键必填：BFF 校验 requiresIdempotencyKey，写操作的 scope 是 (actor, operation)。
  • payment_unknown 是唯一出口是 reconcile：commerce-order 注释写明「the ONLY way out of PaymentUnknown」。

怎么用 / How to use

  • 直接双击 index.html 打开，无需构建、无需起服务、无网络请求。
  • 每屏右侧的说明面板标注了它对应的 API、源码位置与可复现的操作。
  • 数据全部内置在 assets/storefront.js，时间戳相对打开时刻生成。
  • 另一套（游戏线遗留的）运营后台原型在 ../admin-console/。
