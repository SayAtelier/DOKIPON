# 詳細設計書 — Event Engine / Causal Engine

## 1. 入力・出力

入力：`models/architecture.json`、`models/cases.json`、任意の Scenario Delta。出力：グラフの整合性、イベント列、終状態、A/B 比較結果。すべて同一の Stable ID を使用する。

## 2. 決定的実行

計算順は `workflow` が参照する Edge の順番を基本とする。各 Edge で論理時間を更新し、送信元・送信先とイベント ID を出力する。ケース定義に従い在庫拒否・決済タイムアウト等を挿入する。再試行は上限回数を指定する。単一実行の初期状態と入力が同一ならイベント列が一致する。

## 3. エラー契約

| エラー | 結果 | 備考 |
|---|---|---|
| 在庫不足 | `FAILED` | 当モデルの在庫 Guard が拒否 |
| 決済応答不明 | `UNKNOWN` | `payment_unknown`。成功や失敗と同一視しない |
| Node / Edge の無効化 | `BLOCKED` | ルートが無効な場合は以降の伝搬を止める |
| Validator の拒否 | `REJECTED` | Scenario にのみ存在する新規 Guard |
| 一時的障害からの復旧 | `COMPLETED` | 当モデルに定義した一回の Retry + Recovery のみ |

決済結果の再照合は契約上必要だが、現在の Viewer は外部 PSP との実際の再照合処理を行わない。

## 4. セキュリティ

導入できる要素は `Validator`、`Cache`、`Proxy` の限定テンプレート。任意の JS 実行、外部サービス呼出、本番認証情報入力、実決済処理は含めない。端子型は `CommerceMessage`、状態機械の表現は `finite` を必須とする。

## 5. データ・API

実装上の候補となる API は `contracts/openapi.yaml` で確認する。同契約は幂等性キー、少数単位で表す金額、問題レスポンスおよび不明決済状態を規定する。ER 図上のテーブル・属性はまだ実スキーマを確認できていない設計案であり、正式実装に先立ちマイグレーション資料との整合確認を必要とする。
