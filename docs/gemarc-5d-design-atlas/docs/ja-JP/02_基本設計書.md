# 基本設計書 — Canonical Architecture Graph

## 1. 論理構成

ソース内の Client（Flutter Web / App / LINE）、API（Commerce BFF・OpenAPI）、Domain（Identity / Catalog / Cart / Inventory / Order / Payment Adapter）、Platform（Core）を 12 個の Canonical Node として定義する。

空間上の Building・Floor・Room は**理解を補助する意味的レイアウト**であり、実際の建屋、物理ネットワーク、Kubernetes の配置と同一ではない。

各 Node は永続 ID、機能役割、存在性証拠、参照パスを持ち、Edge は方向・ポート・検証レベルを持つ。ワークフローに使用する通信経路は設計モデルであり、実行時トレースとして扱わない。

## 2. 工程図

- UML Component：選択中の構成要素から呼出インターフェースへの関係を検査する。
- UML Sequence：クライアント→BFF→在庫→注文→決済の設計シナリオを表す。
- UML State Machine：注文・決済の Pending / Succeeded / Unknown の区別を表す。
- ER Design：Order と PaymentAttempt の暫定設計を表示する。実 DB の定義確認が終わるまで設計と明記する。

詳細な正式 UML/ER の自動抽出・完全検証は、当バージョンの実装範囲外である。

## 3. ビューの分離

`Logical`、`Deployment`、`Data`、`Security` は空間配置を再投影する View として扱う。これらは 1D～5D の表現レベルとは独立して選択できる。

## 4. イベント処理

イベントが保持する主要情報は `eventId`、`logicalTime`、`sequence`、`nodeId`、`edgeId`、`type`、`detail`。描画はイベント処理結果を参照し、モデルを変更しない。

## 5. 因果実験

Baseline（A）は正式グラフを変更しない。Intervention（B）は元モデルのコピーに対し、モジュール無効化・Edge 無効化・型付きテンプレートの挿入を適用する。

要素挿入時は既存 `Edge` を削除し `source → inserted → target` の 2 Edge に書き換える。入出力の型、状態機械および動作を検証し、A/B の計算結果、最初の差分、終状態を表示する。
