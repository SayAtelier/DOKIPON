## 0. 一句话现状

会话、购物车、订单、库存、支付这五样东西**已经都在 Neon 里**；这一轮补的是
「前端能不能重新拿回自己的数据」和「前台看到的库存是不是台账里的真数」。

**已上线并验证**：五个 store 落库（上一轮）、identity 的 500 修好、CI 全绿。
**这一轮（已在本机验证，未部署）**：会话可续、购物车有归属、前台库存看台账、
结账真的预留库存。

## 1. 这一轮改了什么

### 1.1 会话：刷新之后还是我（A）

会话是顾客的身份：它既是订单的 buyer，也是购物车的 id。会话以前在每个实例的
内存里，刷新一下就丢了——顾客回来变成另一个人，购物车空了，刚下的单找不回。

现在：

| 位置 | 改了什么 |
|---|---|
| `services/crates/commerce-identity/src/session_cookie.rs`（新） | 会话 id 放在 `HttpOnly` cookie 里。**服务端**记，客户端不存——脚本读不到，cookie 也不外泄 |
| `services/crates/commerce-identity/src/lib.rs` | 新增 `GET /v1/sessions/current`（会话校验端点）；签发会话的响应带上 cookie |
| `packages/api_client/lib/src/commerce_api_client.dart` | 新增 `resumeSession()` |
| `packages/storefront_state/lib/src/session_controller.dart` | 启动时先问「我还是我吗」，成功就接着用 |
| `packages/design_system/lib/src/widgets/storefront_app.dart` | 启动时把购物车接回来（以前只在加购时拉，刷新后是空的） |
| `contracts/openapi.yaml` | 契约加 `GET /v1/sessions/current` |

**为什么用 cookie 而不是客户端存**：浏览器自己会带 cookie，客户端什么都不用存
（也就没有新依赖、不用改 Flutter 的构建管线）；`HttpOnly` 让脚本读不到会话 id。

**cookie 的取舍**：cookie 是浏览器的，所以**手机 App（shop_app）拿不到这个连续
性**——它没有 cookie，会话还是每次新签。要在手机上也有，得给 App 加偏好存储。

### 1.2 购物车：有主人了（A）

`cart.owner_id` 这一列在 Neon 里一直没人写，服务端的归属检查其实是死代码。
现在建购物车时把会话 id 写进去，归属检查真的生效（别人的会话拿同一个 id 读
不到，也改不了）。

- `services/crates/commerce-cart/src/lib.rs`：建车时写 owner；**改车时也查归属**
  ——只查不改的话，归属就只是「只读保护」，知道购物车 id 的人照样能往里塞货。
- `services/crates/commerce-cart/src/repo.rs`：仓储接口带上 owner。
- 归属检查放在**领域层**（`CartStore::apply_mutation`），所以内存版和数据库版
  都一样生效——数据库版是把库里的购物车读进 store 再套用同一条状态机。


### 1.3 前台库存显示真值（C）

目录服务里有一份**静态**的库存数（演示数据），销售之后不动——台账说 0，目录
还说 42，顾客被告知「还有货」。

现在目录**问台账**：新增 `commerce_core::StockSource`（接口）+ `StockAuthority`
（HTTP 版），目录的商品列表与详情按台账的在手数算 `availability`，静态数退成
**兜底**（台账问不到时不至于整个商品列表挂掉）。

- `services/crates/commerce-core/src/stock_source.rs`（新）
- `services/crates/commerce-catalog/src/lib.rs`：`availability_of(sku, level)`
- `services/crates/commerce-edge/src/lib.rs`：`InProcessStocks`（进程内版）
- `services/crates/commerce-edge/src/msa/service.rs`：HTTP 版（`INVENTORY_URL`）

### 1.4 结账真的预留库存（B）

这一轮最大的改动，也是**风险最大**的。

订单服务的 Saga 有一个叫「预留库存」的步骤，但它**什么都没预留**——只是自己
编了一个预留 id，台账完全不知道有这回事。于是同一批货可以被卖两次，运营端
看到的在手数永远不动。

现在 Saga 拆成两半，中间留出跨服务调用的口子：

```
begin_submit   建单、幂等门、进入 Reserving 状态   ← 订单 id 在这里就有了
   ↓
（编排层）向库存服务预留：POST /v1/inventory/reservations
   ↓
finish_submit  StockReserved、请求支付、按支付结果走
   ↓
（编排层）确认 → commit 预留；拒绝 → release 预留；未知 → 继续占用
```

关键点：

- **预留用真的订单 id**，台账里记的是「哪一笔订单占了哪些货」；
- 状态机一个字没改（`submit` 仍然是同签名的包装，内部调 begin/finish），
  **已有测试全部不用改**；
- 钱路径上：**支付成功但 commit 失败**不会让接口报错（钱已经付了），只记日志
  让人去对账；**预留失败则整单拒绝**（卖不出去就不卖）；
- 多行订单有多条预留。订单自己的 `reservation_id` 字段只放第一条（契约里
  `reservationId` 是单数，没动），对账时要用的全部预留由**台账**回答
  （`GET /v1/inventory/reservations?order_id=`）。

- `services/crates/commerce-order/src/lib.rs`：`begin_submit` / `finish_submit`
  / `settle_reservations`
- `services/crates/commerce-order/src/repo.rs`：仓储接口同步拆成 begin/finish/abandon
- `services/crates/commerce-core/src/inventory_authority.rs`（新）：
  `ReservationSource` + HTTP 版
- `services/crates/commerce-inventory/src/lib.rs`：`GET /v1/inventory/reservations?order_id=`
- `services/crates/commerce-inventory/src/repo.rs`：`list_reservations`
- `services/crates/commerce-edge/src/lib.rs`：`InProcessReservations`

### 1.5 顺带修的

- 库存的种子改成**把在手数补回演示值**（`GREATEST`）：演示店不会几周下来把
  货卖光。两次启动之间台账是真话（卖一件少一件），启动时补回演示数据。
- `inventory_reservation` 上表级 `UNIQUE (order_id, sku_id)` 与状态机打架
  （状态机说「释放之后可以再预留」），换成**只约束活跃预留**的部分唯一索引。

**本机结合测试看到了什么**（这是「数据库里的真相真的动了」的证据）：

```
--- 台账（结账前） ---   sku-bra-01  onHand 42  reserved 3  available 39
--- 台账（结账后） ---   sku-bra-01  onHand 36  reserved 3  available 33
--- 目录说的 ---          sku-bra-01  availability = in_stock（问台账问来的）
```

在手数少了 6 件 = 3 笔确认订单 × 2 件，正是 e2e 脚本里三笔走到 `confirmed` 的
订单（happy path、换个买家再来一次、未知支付后对账确认）。被拒的那笔把货退回，
`payment_unknown` 那笔先占着——所以 `reserved` 没变。**这就是 B 想要的：结账真的
预留库存，而不是自己编一个预留 id。**

**顺带修掉的 clippy warning**（CI 是 `-D warnings`，不改就是红的）：目录里一个
多余的 clone；订单服务的 `SubmitStart` 两个分支大小差太多（大的那个装箱）；八个
handler 的 `State` 三元组太复杂（起了个 `OrderState` 的名字）。

### 2.3 已知要小心的

- **内存占用**：本机同时还有别的项目的 cargo 在编译，`cargo` 偶尔会撞
  `LNK1104`（链接器写 `E:\DevCache\cargo\target` 时被杀软扫文件占住）——
  **重试即可**，不是代码问题。内存紧的时候编译会非常慢。
- **订单 Saga 的 begin/finish 拆分**是本轮最容易出错的地方：改了
  `OrderStore`、`OrderRepository`、handler 三处。`submit` 的签名没变，所以
  老测试没变；新增的 `begin_submit`/`finish_submit` 在
  `commerce-order/tests/order_repo_test.rs` 里有配套的 `submit()` 辅助函数
  （模拟 handler 的两步）。
- **多行订单的预留**只记了第一条在订单上，其余的在台账里（见 1.4）。
- **`GET /v1/inventory/reservations` 必须带 `order_id`**：不带就 400
  （`inventory.missing_order_id`）。这是故意的——不带参数就返回别人的订单占了
  多少货，是不该开的口子。
- **会话 30 分钟过期**（设计如此）。所以「隔天回来还是我」仍然不成立——
  那需要把订单的 owner 从会话 id 换成 LINE 的 subject，是设计变更不是 bug
  （UAT 的 README 末尾写了）。
